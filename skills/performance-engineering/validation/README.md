# Validation record

Read [report.json](report.json) for commands, compiler versions, stdout, failures,
and skips from the actual validation run. The report is generated by
`python3 scripts/verify.py` from the skill directory; an unavailable tool or
target is not a passing test.
By default, each run overwrites the file, so the record describes one host.
Use `--output <path>` to retain a separate report for another host or run. Re-run
it on every platform you intend to claim; separate reports do not automatically
establish coverage for the same revision.

The committed record was produced on 2026-09-05 on macOS/AArch64 (Apple clang 21,
rustc 1.98.1, Python 3.10) with the result `PASS_WITH_SKIPS`. See the
machine-readable report for exact executed results. The tests are correctness
checks, not application performance benchmarks.

The [2026-09-06 systems/prevention validation note](books-update-2026-09-06.md)
records separate x86-64/Linux checks, not the run stored in `report.json`. Read
its scope and skips independently; its results are not merged into this record.

## Coverage and limitations

C++ release tests are run with each available GCC/Clang compiler; on macOS both
`g++` and `clang++` resolve to the same Apple Clang driver, so that is one
toolchain, not two. A separate AddressSanitizer/UndefinedBehaviorSanitizer build
checks the native examples. LeakSanitizer is requested only on Linux, so the
committed record does **not** check for leaks. The native test executable prints
which byte-search backends were actually exercised; on this host those were the
scalar, dispatch, and NEON paths.

The x86-64 SSE2/AVX2 kernels and the generated-assembly instruction inspection
require an x86-64 host and were **not** compiled or executed for the committed
record. NEON likewise requires native AArch64 execution; an x86-64 run does not
compile or execute the guarded NEON implementation.

Rust compilation/testing requires Cargo and rustc. A missing Rust toolchain means
the Rust source was **not compiled or executed**, even when related C++ algorithms
passed.

The logarithm checks compare sampled positive u32 inputs against platform libm.
The derived series truncation bound is a real-arithmetic result, not a certified
bound for every compiled floating-point operation. Neither sampled agreement
nor sanitizer success is a full proof of correctness.

Python tests use explicitly synthetic data to exercise normalization, confidence
interval decisions, input validation, sample-count handling, and per-case gates.
Those values are not performance observations.

No user application, production corpus, allocation/RSS profile, or service load was
supplied. **No speedup, memory saving, or cross-platform performance claim is made
by this package.** Re-run the relevant native tests, inspect generated code, and
measure the consuming application before adoption.
